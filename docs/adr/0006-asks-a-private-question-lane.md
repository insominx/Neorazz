# 0006. Asks: a private question lane

Date: 2026-11-14  
Status: Proposed. A1 and "The deck" are amended by `0007` (the presenter's drawer).

## Context

People in a room who do not want to interrupt, cannot yet phrase a question, or are shy should be able to type a question on the phone they already joined with. The presenter reads the questions privately and follows up, in the moment or afterwards. Before Razzia he used a separate web page for this.

A lecture room (`0002`) already has everyone joined once, by name, on one socket each, and it already runs a second lane beside the quiz (polls, `0004`, `0005`). In a deck the host's screen is the projector, so anything the host page or the deck frame is told can end up in front of the room. The room is small (20 to 25 people), so a channel that is anonymous in storage can still point at its author through timing or wording.

The presenter decided (razzia-workflow task 0014, 2026-11-14): the projector shows a count only, never the text; questions are anonymous by default, to him as well, with an optional "add my name"; a question button on the phone opens a small fold-out, offered on the waiting screens and hidden while a timed question runs; each question is new, seen or answered, and is kept until he deletes it; no upvotes and no public feed; the count is live; it clears only when he taps **Got it**.

## Decision

An **ask** runs in its own lane beside the quiz and the polls, with its own state on the server, its own events and its own client store. The quiz's status machine, scoring, caches and payloads, and the poll lane, are not touched. The code calls it the ask lane (`Ask`, `AskManager`, `features/ask`, `config/asks/`, events `ask:*` and `asks:*`, bridge feature `asks`), because "question" already means a quiz question. People in the room read "question".

### Privacy rules

- **A1. The text never reaches a projected surface.** An ask's text and any name go only to sockets that watch the inbox with a manager login. They are never in `manager:lectureState`, a room broadcast, a bridge message, or a manager page other than the inbox route. Nothing on a projected page opens or names the inbox. The inbox starts curtained (counts only, with **Show questions**) and curtains again whenever the page is hidden or loses focus. It refuses to draw inside a frame. It keeps no asks in browser storage.
- **A2. The room learns a capped, live count and nothing else.** The host page and the deck are told `{ waiting, open }`: `waiting` is the number of new asks, capped at 10 (drawn as "9+"), and `open` is whether phones can send. It changes the moment a question arrives, and the phone says so.
- **A3. An unsigned ask has no author anywhere.** The ask and its saved record hold no client id, socket id or name. Ask and record ids are random (`nanoid`), never time-ordered: a uuid v7 would carry the millisecond the ask arrived. The ask handler logs nothing about an ask (no text, name, client id or socket id) on success, refusal or a failed write. Rate counters and nonces are in memory, per room, never linked to an ask and never saved.
- **A4. A signed ask carries the seat's join name**, taken from the server's player record, never from the payload.
- **A5. Phones never receive another person's ask.** No event to a phone or to the room carries an ask.
- **A6. The honest limit.** "Anonymous" means there is no record of who sent it. It is not a guarantee. The projected count moves when a question arrives, so people nearby may guess who just asked. The presenter may see it arrive while facing the room. Wording can give someone away in a room of 20. The host's ordinary logs record connects and reconnects by name with a time, so the times saved with an ask are rounded down to the minute. Questions are kept until the presenter deletes them. The phone says the plain version: only the presenter can read it, no name is attached unless added, the screen shows when a question arrives, and questions are kept so the presenter can read them later.

### The lane

- **One record per room.** A lecture room's `AskManager` holds its record, the box (`open`), per-seat counters and recent nonces. It imports nothing from `RoundManager`, `PollManager`, `Game` or storage; `Game` hands it a save function and an `onChanged` callback. A record (`config/asks/<id>.json`, `{ id, gameSubject, date, asks }`) is created on the room's first ask. A new room (Restart quiz, a host restart, the next session) starts with an open box, a count of 0 and no record. The box belongs to the room and is never saved.
- **No activity lock.** An ask does not take the room. The server accepts one in any phase of a lecture room; hiding the button while a question runs is the phone's job.
- **Sending.** `ask:send { gameId, text, signed, nonce }` is acked with an outcome: `accepted`, `notLecture`, `notPlayer`, `closed`, `invalid`, `tooFast`, `tooMany` or `full`. Text is 1 to 500 characters after control characters are stripped (line breaks kept) and the ends trimmed. One ask per seat per 15 s, 10 per seat per room, 500 per room. A seat costs nothing to invent, so the caps are a speed bump and the presenter's pause is the defence. The phone sends a random nonce per draft, and a nonce accepted in this room in the last 30 minutes answers `accepted` again and stores nothing, so a send repeated after a lost acknowledgement cannot make a duplicate. Validator messages never quote the input.
- **The box.** `ask:sync { gameId }` is answered with `ask:box { open }`, or `ask:box null` when the room is not a lecture room or the sender is not one of its players. `ask:box { open }` goes to the room whenever the box opens or closes. The phone syncs when its game changes and after every `player:successReconnect`, because this lane changes no player payload. The game's manager may set the box (`manager:setAskBox { gameId, open }`), and so may an inbox watcher (`asks:setOpen`).
- **What the host page and the deck see.** `LectureState.asks` (`{ waiting, open }`) is pushed through `manager:lectureState` when either value changes, and so rides `gameCreated` and `successReconnect` like the rest of the lecture state. It is absent until the lane first changes (the first ask, or the box closing), so a lecture room without asks sends exactly what it always did; absent means `{ waiting: 0, open: true }`.
- **Write-through storage.** Every change to a record writes it atomically (`writeFileAtomic`), because the host sleeps when idle and a restart loses live rooms. A failed write is logged without content, the record stays in memory marked not saved, and the next change or the room's close tries again. Listing never throws. Every record id from a client passes `isSafeId`. The files are never served.
- **The inbox.** `/manager/questions`, behind the manager login, laid out for a phone, and not a tab on any other manager page (the deck's frame can show those on the projector). A socket that sends `asks:watch` with a login joins a watcher set and gets `asks:live`: every live lecture room (with its record, if any, so a room without asks can still be paused) and the earlier records' summaries. Each change in a live room is sent to every watcher at once (`asks:room`). Before every send the login is checked with `Manager.peek`, which does not refresh it; a lapsed watcher gets `manager:unauthorized` and is dropped. A disconnect or `manager:logout` drops a watcher, and the page watches again on every connect. Watching never makes a socket the game's manager (`0002`'s two-tabs hazard). The inbox's actions (`asks:mark`, `asks:markAll`, `asks:remove`, `asks:setOpen`, `asks:recordGet`, `asks:recordDelete`) need the login and answer through an ack. A live room's record cannot be deleted (`live`). Nothing is marked seen by being shown. No sound, no vibration; text is drawn as text only. The lane adds nothing to `ManagerConfig`.
- **The phone.** A question button in the player footer, offered (`canAsk`) on `WAIT` except `game:waitingForAnswers`, on `SHOW_RESULT`, `SHOW_STANDING` and `FINISHED`, while the box is open and no poll shows. When it is not offered it keeps its space (`visibility`), so the footer's height never changes as a question starts. The fold-out is a dialog drawn above the poll overlay and outside what a poll makes inert, so it closes whenever `canAsk` turns false; the draft, its "Add my name" switch and its nonce are kept in the tab's session storage until sent.
- **The deck.** The bridge lists `asks` in `features`, reports `BridgeState.asks` (`{ waiting, open } | null`), and takes one command, `askBox { open }`. `askBox { open: false }` is held for the frame's life and sent again (`manager:setAskBox`) each time the frame becomes a game's manager (create, resume, reattach), so a deck that switches the lane off keeps it off in every room it makes. `askBox { open: true }` opens the box once and drops the hold, so a reattach never undoes a pause from the inbox. Protocol version stays 1. No bridge message carries an ask's text or a name. The deck's side is the course repository's shared host runtime (`Tools/razzia-host/`), as for `0002` and `0005`.

## Alternatives considered

- **Asks as a kind of poll, or a status.** Rejected for the reasons in `0004`: the quiz's statuses, reconnect caches and screens are the surface a lane exists to leave alone.
- **The box state on the join and reconnect payloads.** Rejected: `game:successRejoin` carries a bare id, `game:successJoin` is emitted inside `PlayerManager.join`, and both would change quiz-lane code. `ask:sync` costs one event.
- **Text on the projector, a public feed, or upvotes.** Not asked for, and each would put words in front of the room.
- **A delayed or coalesced count**, so the count does not point at whoever just asked. Both reviews of the plan asked for it. The presenter chose a live count; A6 and the phone's line say what that costs.
- **One record per lecture**, continuing a record across rooms of the same subject. Rejected: a rehearsal's or a test room's questions and pause would follow into the real session, two live rooms could write one file, and it would defeat Restart quiz. The inbox orders records with unread asks first instead.
- **A link or button to the inbox from the deck's panel or the host page.** Rejected: a window opened from a projected page lands on the projector.
- **An idle timer on the curtain.** Rejected: a phone on the podium must stay readable.
- **A Socket.IO room for watchers.** Rejected: a set checked before every send can drop a lapsed login; a room cannot.

## Consequences

- Common, socket and web ship together, as before. An old phone page never offers the button; a new page on an old server never gets an answer to `ask:sync`, so it never offers it either. An old deck ignores `asks`; a new deck on an old Razzia sees no `asks` feature and sends nothing.
- A host restart loses live rooms, their boxes and the logins, as it does for games (`0002`). Saved records survive in the config volume and are listed as earlier records. A record whose write failed and was not retried before the restart is lost; the inbox showed it as not saved.
- The inbox needs the password on each host after it wakes, because logins live in memory and each host is its own origin.
- Records are kept until the presenter deletes them. Signed asks keep a person's name with their words on the host's volume.
- Each change of `{ waiting, open }` is one more `manager:lectureState`, and so one more deck `status`. Changes that leave both values as they were (marking a seen ask answered, a repeated send) send nothing to the host page.
- Redeploying a build without the lane is safe over a volume with `config/asks/`: the image seeds only quizzes and the old build never reads the folder.
- Phone and inbox copy is in `ask.json` in all six languages. The es, fr, it, de and ja strings are checked for key parity only and want a native reader.
